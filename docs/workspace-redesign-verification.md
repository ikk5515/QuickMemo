## Implementation boundaries

- Preserve encrypted note/folder data and existing auth, rules, sanitizer, recovery and security headers.
- One owner has one public wiki root with an atomic unique custom slug; folders/notes extend that tree. Explicit publication grants stay separate from edit rights.
- One live Markdown editing surface, independent in-memory document/undo/dirty/save/scroll state, no plaintext/key browser persistence.
- All open wiki documents remain independently addressable, closable and collapsible with vertical title strips and measured motion.
- UI dimensions and collapse preferences are non-sensitive metadata. Inspect server preference support before choosing persistence.
- Legacy public snapshots must remain readable until an owner explicitly migrates them. Never delete original notes or silently broaden publication scope.
- Production validation must use explicitly labeled synthetic notes/folders/wiki data. Existing personal data is not a test fixture.

## Architectural decisions and current measurements

- Retain CodeMirror 6: it preserves Markdown source and supports existing syntax, search, image and sanitizer extensions. An editor replacement would duplicate already secured persistence and recovery. Document sessions are memory-only and bounded; key/authority changes clear them.
- Owner Wiki runs through `VaultPage(surface="wiki")`, avoiding a second editor/save implementation. Public Wiki receives only the staged authorized read projection and never mounts a writable editor.
- Custom slugs are ASCII lowercase, 3–40 characters, with a reserved-name denylist. Internal publication and source IDs are not used in the public browser URL. Renaming invalidates the old address; another owner cannot claim its tombstone.
- Publication remains an explicit grant. Folder grants include descendants; individual-note grants expose the note at the public root. Automatic publishing cannot add a new grant. Original encrypted records remain unchanged.
- Sidebar preference API accepts only width/collapsed metadata, selects its document from authenticated UID, checks same origin/App Check/active user and bounds, and uses CAS/rate limiting. Local fallback stores no note, key or plaintext body.
- Unit benchmark on this machine (not a production latency claim): 120 notes, full baseline 183.98ms; metadata refresh 0.78ms with 0 RSA/0 AES; one body update 1.76ms with 0 RSA/1 AES. A 5,000-note metadata refresh eliminated 5,000 RSA and 10,000 AES calls. Logs `/tmp/qm-redesign-unit.log`.
- The first integration run exposed 14 failures in three tests using the former WikiPage/mode/panel behavior. These were resolved while retaining permission and source-fidelity assertions; the final full-suite result below supersedes that run.

## Deployment boundary update

- Vercel Hobby supports 12 API functions for this Vite deployment. Preferences now dispatch only through `POST /api/vault-integrity?resource=workspace-preferences`; the underscore helper is not an additional function. Runtime API count is 12. The Functions guard and a 12-pass/13-fail fixture regression enforce this limit.
- Preferences retain a separate marker, same-origin, active-user and App Check checks, a 2KiB body bound, UID-derived document lookup and metadata-only projection. Missing, duplicate and unknown resources cannot invoke this branch as an integrity action.
- No new environment variable, credential, Firestore index/Rule or bulk migration is required. New owner/slug/preferences documents use the existing server REST identity and remain denied through client Firestore access. Legacy migration is an explicit user action.
- The detailed current URL/publication contract is in `docs/wiki-publishing.md`. This architectural update is not a production deployment claim.
